AquaVistawAquaVista
AquaVista / AquaVista is a mAquaVistaate study assistant platform that helps AquaVista consultants and municipal project users review uploaded project data, ask questions through Ask AVA, generate structured outputs, view basic AI-generated charts, and save useful Ask AVA outputs to a project dashboard.
The application sits between AquaVista’s data collection process and downstream rate modeling/reporting process. It does not replace the final rate study, rate model, or formal report.
The goal of the PoC is to make project data easier to review, query, summarize, visualize at a basic level, and reuse.
This PRD removes the previous concepts of:
Auto-generated persistent charts on upload
Interactive dashboard charts
Dashboard filters
Advanced chart configuration
Anomaly detection
Anomaly sections or anomaly tabs
Downloadable files generated from chat responses
The dashboard is now a curated space that only displays content pinned from Ask AVA.

2. Product Naming
The AI assistant experience should be branded as:
Ask AVA — AquaVista Assistant
Use Ask AVA in navigation and compact UI labels.
Use AquaVista Assistant in fuller page titles, helper text, and onboarding copy.
Avoid using generic “Chat” as the main product label unless required for internal or technical clarity.

1. Overview
AquaVista
AquaVista Solutions, a small water and sewer consulting firm, performs rate studies for municipal utility clients. Their current workflow involves manually reviewing each municipality's financial statements, customer billing data, capital improvement plans, and rate tables in Excel to identify anomalies, model rate scenarios, and produce recommendations. This is time-consuming and inconsistent across projects.
AquaVistaAquaVista
This PRD defines a Claude-powered Proof of Concept (PoC) web application that allows AquaVista consultants and their municipal clients to interact with baseline municipal data through a chat interface, view a persistent set of charts derived from that data, and surface anomalies that warrant further investigation. The PoC is the analysis layer only — it does not replace AquaVista's downstream rate modeling, report writing, or client deliverables.

This PRD covers Phase 1 of the build: a working application with auto-generated dashboard charts, anomaly detection, and a text-only chat interface that sends the full baseline data and full chat history to the LLM with every call. Phase 2 (static charts in chat, pinning from chat) and Phase 3 (interactive charts, RAG-based retrieval, history summarization) are described as future scope in sections 10 and 11 to give engineering and the client a shared view of the trajectory.
Product ContextAquaVista
The application sits between AquaVista's data collection step (gathering documents from municipalities) and their analysis-and-recommendation step (designing rate structures and writing reports). It accelerates the &quot;review and understand the data&quot; phase that currently happens manually in Excel.
AquaVista
The application is multi-tenant by project. Each project represents one municipality. A single AquaVista consultant acts as super admin across all projects. Each project has its own set of users (typically representatives from the municipality being studied) who can chat with the LLM about that project's data and view the project's persistent charts.
GoalAquaVista
Enable a AquaVista consultant to set up a municipal project, upload baseline data, and immediately see auto-generated visualizations and flagged anomalies, while allowing both the consultant and the municipal client to ask follow-up questions of the data through chat.


2. Users / UsAquaVista
Super Admin (SwAquaVistaonsultant)
Description: A AquaVista Solutions consultant who runs rate studies. There is a small number of super admins; for the PoC, treat as a single role with shared capabilities.
Primary goals: Set up new municipal projects, upload and maintain baseline data, interact with the LLM to analyze data, curate which charts are pinned to a project dashboard, and oversee project users' activity.
Permissions or access level: Full access. Can create projects, add users to projects, upload and re-upload baseline data, chat with the LLM in any project, unpin default charts from the dashboard, and view the chat history of any user in any project. (Pinning charts from chat is Phase 2.)
Project User (Municipal Client)
Description: A representative of the municipality being studied (e.g., town manager, finance director, board member). Invited to a specific project by the super admin.
Primary goals: Understand the municipality's financial and consumption picture by viewing the project's persistent charts and asking follow-up questions via chat.
Permissions or access level: Read access to the project's baseline data and dashboard charts. Can start private chats with the LLM about the project's data. Cannot upload data, cannot manage charts, cannot see other users' chats, cannot create projects or add users.

Role-based differences are material: only super admins can upload data and unpin default charts; only super admins can view other users' chats. All other behavior is identical between the two roles.


3. Terminology
Term
Definition
Project
A workspace scoped to a single municipality. Contains baseline data, persistent charts, and user chats.
SuAquaVista
A AquaVista consultant user with cross-project administrative access.
Project User
A user invited to a single project; typically a municipal stakeholder.
Baseline Data
The set of source datasets uploaded for a project: customer allocation/billing, financial snapshot, CIP register, rate table, demographics.
Financial Snapshot
A multi-year financial dataset for the municipality covering revenues, expenses, capital accounts, and profit/loss. The only required baseline dataset for project creation.
Customer Allocation / Billing Data
Per-account billing records including account class, period, consumption (gallons), and charges.
CIP Register
Capital Improvement Plan dataset listing planned capital projects.
Rate Table
The municipality's existing rate structure (tiers, base charges, volumetric rates).
Demographics
Census/ACS-derived data such as median household income, household count, and age distribution.
Persistent Chart
A chart attached to the project dashboard, visible to all users in the project. Generated either automatically on baseline upload or pinned by the super admin from a chat.
Anomaly
A data point or trend flagged by the LLM as warranting attention (e.g., expense category growing faster than revenue, line item exceeding budget by significant margin, revenue decline year-over-year).
Chat
A private conversation between a single user and the LLM, scoped to a single project.
Re-upload
Replacement of a baseline dataset for a project. Triggers removal of all pinned charts in the project.
Activation
The one-time process by which a newly invited project user clicks an emailed link and sets their password, after which they can log in. Super admins do not go through activation; their credentials are bootstrapped at deployment.
Phase 1
The scope of this PRD: text-only chat responses, full baseline context and full chat history sent with every LLM call. The current build target.
Phase 2
Future scope (documented in section 10): static charts in chat responses and pinning chat-generated charts to the dashboard. Context-loading strategy unchanged from Phase 1.
Phase 3
Future scope (documented in section 11): interactive charts with filters, RAG-based context retrieval, and summarized chat history.


4. Scope Summary
In Scope
User authentication (login, logout) for super admins and project users.
Account activation flow: new project users receive an email with an activation link and set their own password before first login.
Password reset flow: any user can request a password reset via email link at any time.
Project creation and management by super admin (create project, add users, remove users).
Project selection screen after login (users see only projects they belong to; super admin sees all projects).
Baseline data upload via CSV or Excel file, supporting the five dataset types listed in Terminology.
Re-upload of any baseline dataset, replacing the prior version.
Auto-generation of a default set of persistent charts when baseline data is first uploaded.
Anomaly detection on the financial snapshot, surfaced as a dedicated section on the project dashboard.
Text-based chat interface scoped to a project, where users can ask questions about the project's baseline data and receive text responses (no charts or visualizations in chat responses).
Visibility of all persistent charts to all users in the project.
Super admin ability to view any user's chat history within any project.
Removal of all pinned charts on re-upload of any baseline dataset.
Out of Scope
Data versioning or history (re-uploads overwrite prior data; no version log retained).
Exports of any kind (no PDF, Excel, CSV, or image export of charts, data, or chat content). Users can ask the LLM to format responses for copy-paste, but the application provides no export feature.
Billing, payments, or subscription management (separate concern outside the PoC).
Excel push/pull integration or write-back to source files.
Direct integration with municipal billing systems, GIS, or other tAquaVista services.
Multi-firm tenancy: the application supports one consulting firm (AquaVista) with multiple projects. No firm-level isolation is built.
In-app or activity notifications of any kind (e.g., &quot;your data was updated&quot;, &quot;a new chart was pinned&quot;). Transactional system emails for account activation and password reset are in scope; everything else is excluded.
Mobile-specific UI; the PoC targets desktop browsers.
Permission tiers beyond super admin and single project-user role.
Automated report generation, proposal writing, or client deliverable production.
Charts, visualizations, or any non-text content rendered inline in chat responses. The chat in Phase 1 is text-only.
Pinning charts generated in chat to the dashboard. (Auto-generated default charts on upload are the only pinned charts in Phase 1.)
Retrieval-augmented generation (RAG) or selective context loading. The full baseline data context and full chat history are sent to the LLM with every request in Phase 1.
Chat history summarization or compression.
Comparison views across projects/municipalities.
Shareable project links or public/unauthenticated access. Project access is granted exclusively by the super admin adding a user to the project (Story 2.2).
Implementation Boundaries
No data versioning. Re-uploads overwrite prior data and remove pinned charts; prior state is not recoverable.
No export functionality of any kind from the application UI.
No permission differentiation among project users; all project users have identical capabilities.
No automated activity notifications. Transactional emails for activation and password reset are the only system-generated emails.
No write-back to source data formats (CSV, Excel).
The LLM is the analysis engine; the application does not perform analysis outside the LLM (no separate analytics pipeline, no statistical service).


5. Assumptions and Constraints
Assumptions
All baseline data is provided by the super admin in clean CSV or Excel format. Data quality and schema correctness are the super admin's responsibility.
The financial snapshot is structured consistently enough across municipalities that the LLM can reliably identify revenue, expense, and capital account categories from it.
The LLM (Claude) is capable of generating the auto-default charts and detecting the anomalies described in this PRD when given the financial snapshot.
Authentication can be implemented using standard email/password or equivalent; no SSO requirements for the PoC.
A transactional email service (e.g., SendGrid, Postmark, AWS SES) is available for delivering activation and password reset emails.
Super admin credentials are provisioned at deployment time via configuration (bootstrap) and delivered to the super admin out of band. There is no in-app super admin signup flow. Super admins can change their password at any time via the standard password reset flow (Story 1.4).
The user base is small (one consulting firm, single-digit projects, single-digit users per project) and performance optimization is not a PoC concern.
Baseline file sizes are expected to grow as more projects come on board; future municipalities may have customer billing datasets significantly larger than the ~22,000 lines seen in the Strasburg example. The upload pipeline and chart generation must handle this without rework.
All users access the application via modern desktop web browsers.
Constraints
One project equAquaVistanicipality. A single project cannot span multiple municipalities.
One firm only (AquaVista). The application architecture need not support multiple consulting firms.
All data and chat content is scoped per project; no cross-project queries or shared resources.
LLM operating costs are absorbed by the operator; the PoC does not include guardrails, metering, or usage limits.
Chats are private to each user. Only the super admin can view another user's chats.
Only the super admin can upload data and pin charts.


6. User Flow / Journey Framing
Super admin receives bootstrap credentials out of band (provisioned at deployment) and logs in.
Super admin creates a new project for a municipality.
Super admin adds project users (municipal stakeholders) to the project by email. Each new user receives an activation email with a link to set their password.
New user clicks the activation link, sets their password, and is taken to the application (logged in).
Super admin uploads baseline data (at minimum, the financial snapshot; optionally, the other four datasets).
System processes the upload and auto-generates the default set of persistent charts and the anomaly section.
Super admin views the dashboard, reviews the auto-generated charts and anomalies.
Super admin opens a chat within the project and asks free-form questions about the data, receiving text responses from the LLM.
A project user logs in, sees the list of projects they belong to, and selects the project.
Project user views the same persistent dashboard the super admin curated, and starts their own private chat to ask text-based questions of the project's data.
Any user (super admin or project user) can request a password reset at any time via a &quot;Forgot password&quot; link on the login screen, receiving a reset email.
When new baseline data becomes available (e.g., updated billing data for a new month), the super admin re-uploads the relevant dataset.
System removes all pinned charts in the project (including the auto-generated defaults), re-runs auto-generation on the updated data, and produces a fresh dashboard.

User Story 1.1: User Login
Objective
A user (super admin or project user) authenticates and reaches the project selection screen.
Detailed Functional Behavior
The user enters an email and password on the login screen and submits.
The login screen displays a &quot;Forgot password?&quot; link that initiates the password reset flow (Story 1.4).
On successful authentication, the user is taken to the project selection screen.
On failed authentication, an error message is displayed and the user remains on the login screen.
Logic / System Behavior
System validates credentials against the user store.
System establishes an authenticated session.
System determines the user's role (super admin vs. project user) for subsequent authorization.
Validations
Email must be in valid format.
Password must be provided.
Failed login displays a generic error (&quot;Invalid email or password&quot;) without disclosing which field is wrong.
Dependencies
User accounts must exist and be activated. Project users are provisioned via the super admin (Story 2.2) and activated via Story 1.3. The super admin is provisioned at deployment with credentials delivered out of band.
Edge Cases / Exception Handling
Repeated failed logins: out of scope (no lockout, no rate limiting for PoC).
User attempts to log in before activating their account: login fails with a generic error (the user should use the activation link from their email).
Non-Goals / Exclusions
SSO, multi-factor authentication, and account self-registration are out of scope.
Acceptance Criteria
Given valid credentials, when the user submits the login form, then the user is taken to the project selection screen.
Given invalid credentials, when the user submits the login form, then a generic error message is shown and the user remains on the login screen.
The system must establish a session that persists across page reloads until logout.


User Story 1.2: Project Selection
Objective
The authenticated user picks which project to enter.
Detailed Functional Behavior
After login, the user sees a list of projects.
A super admin sees all projects in the system.
A project user sees only the projects they have been added to.
The user selects a project and is taken into that project's workspace (dashboard).
Logic / System Behavior
System queries projects based on the user's role and membership.
For project users, only projects where the user appears in the project's user list are returned.
ValidationsAquaVista
If a project user has no projects, an empty-state message is shown (&quot;You have not been added to any projects yet. Contact your AquaVista consultant.&quot;).
A super admin with no projects sees an empty-state message with a prompt to create a new project.
Role-Based Behavior
Super admin: sees all projects; can create a new project from this screen (Story 2.1).
Project user: sees only their projects; cannot create projects.
Dependencies
At least one project must exist for project users to have anything to select.
Edge Cases / Exception Handling
A user belongs to exactly one project: the user can still see the selection screen and click into the project (no auto-redirect for the PoC).
Non-Goals / Exclusions
Project search, filtering, sorting, or favorites are not included.
Acceptance Criteria
Given a project user with two project memberships, when the user logs in, then the user sees exactly those two projects listed.
Given a super admin, when the super admin logs in, then the super admin sees all projects in the system.
Given a project user with no memberships, when the user logs in, then an empty-state message is displayed.
When the user clicks a project, then the user is taken to that project's dashboard.


User Story 1.3: Account Activation
Objective
A user added to a project by the super admin activates their account by setting a password.
Detailed Functional Behavior
When the super admin adds a new user to a project (Story 2.2), the system sends an activation email to the user's email address.
The email contains a unique activation link.
The user clicks the link and lands on an activation page in the application.
The activation page asks the user to set a password (with confirmation).
On successful submission, the user's account is activated, the password is stored, and the user is automatically logged in and taken to the project selection screen.
Logic / System Behavior
The activation link contains a token tied to the user's account. The token is single-use and expires after a reasonable window (e.g., 7 days).
Once activated, the account allows standard login (Story 1.1).
If the user is added to additional projects later, no new activation email is sent — the existing account is just associated with the new project.
Validations
Password must meet basic strength requirements (e.g., minimum 8 characters; specific rules to be set by the implementation team).
Password confirmation field must match the password field.
Activation token must be valid and unexpired.
Role-Based Behavior
Activation flow applies only to project users added via Story 2.2. Super admins are provisioned at deployment with pre-set credentials (no activation email).
Dependencies
Email delivery infrastructure must be available (transactional email service).
The user must have been added to at least one project by the super admin.
Edge Cases / Exception Handling
Expired activation token: the activation page displays an error and offers the user a way to request a new activation email (the user enters their email; system re-sends the activation link if the account exists and is not yet activated).
User has already activated and clicks the link again: redirect to login with a message that the account is already active.
User does not receive the activation email: super admin can trigger a re-send from the user management section (Story 2.2).
Non-Goals / Exclusions
No social login or OAuth-based activation.
No identity verification beyond email link click.
Acceptance Criteria
Given a new user added to a project by the super admin, when the system completes the add operation, then an activation email is sent to the user's email address.
Given a valid activation link, when the user clicks it and sets a password, then the account is activated and the user is logged in.
Given an expired activation link, when the user clicks it, then an error is shown and the user is offered the option to request a new link.
Given an already-activated account, when the user clicks an old activation link, then the user is redirected to login with an informational message.
The system must not send a new activation email when an already-activated user is added to an additional project.


User Story 1.4: Password Reset
Objective
Any user can reset their password if they forget it or want to change it.
Detailed Functional Behavior
The login screen displays a &quot;Forgot password?&quot; link.
Clicking the link takes the user to a &quot;Request password reset&quot; page where they enter their email.
The user submits the form and the system sends a password reset email to the address (if it corresponds to an active account).
The email contains a reset link that opens a &quot;Set new password&quot; page in the application.
The user enters and confirms a new password and submits.
On success, the user is logged in and taken to the project selection screen.
Logic / System Behavior
The reset link contains a single-use token tied to the user's account, expiring after a reasonable window (e.g., 1 hour).
The previous password is invalidated immediately on successful reset.
Active sessions for the user are invalidated on password reset (force re-login on other devices).
For email-not-found cases, the system displays a generic success message regardless (&quot;If an account exists for this email, you'll receive a reset link shortly&quot;) to avoid email enumeration.
Validations
Email must be in valid format on the request page.
New password must meet the same strength requirements as activation (Story 1.3).
Password confirmation must match.
Reset token must be valid and unexpired.
Role-Based Behavior
Available to all users, including super admins.
Dependencies
Email delivery infrastructure must be available.
Edge Cases / Exception Handling
Expired reset token: the reset page displays an error and offers the user the option to request a new reset link.
Reset link used twice (e.g., user clicks an older link after using a newer one): the second click shows an &quot;invalid or expired&quot; error.
User requests multiple reset emails in quick succession: only the most recent token remains valid; prior tokens are invalidated.
Non-Goals / Exclusions
No security questions, recovery codes, or alternate recovery channels.
No rate limiting on reset requests for the PoC (deferred).
Acceptance Criteria
Given a user on the login screen, when they click &quot;Forgot password?&quot; and submit their email, then a reset email is sent if the account exists.
The system must display a generic success message regardless of whether the email exists, to prevent email enumeration.
Given a valid reset link, when the user sets a new password, then their old password is invalidated and they are logged in with the new password.
Given an expired reset link, when the user clicks it, then an error is shown and the user can request a new link.
A super admin must be able to use the same password reset flow as a project user.

Epic 3: Baseline Data Upload
Purpose
Get municipal data into the project so the LLM and chart generator can work with it.
User Flow Placement
Step 4, and step 11 (re-upload).


User Story 3.1: Upload Baseline Data
Objective
The super admin uploads one or more baseline datasets for a project.
Detailed Functional Behavior
Within a project, the super admin opens a &quot;Data&quot; section.
The super admin sees five upload slots, one for each baseline dataset: financial snapshot, customer allocation/billing, CIP register, rate table, demographics.
For each slot, the super admin can upload a CSV or Excel (.xlsx) file.
The super admin must upload the financial snapshot before any charts can be generated; the other four are optional and can be added at any time.
Each slot shows its current status: empty, uploaded (with timestamp and source filename or sheet URL), or processing.
Logic / System Behavior
On upload of the financial snapshot, the system triggers auto-generation of the default persistent charts (Epic 4) and the anomaly section (Epic 5).
On upload of any other dataset to an empty project (financial snapshot already present), the system makes that data available to the LLM and may extend the auto-generated charts (e.g., adding a customer-billing chart when billing data is uploaded — see Story 4.1).
Data is parsed and stored in a form the LLM can query and the chart generator can read.
Validations
File must be CSV or Excel (.xlsx) format.
Financial snapshot is required for the project to produce charts; until it is uploaded, the dashboard displays an empty state instructing the super admin to upload it.
Each upload slot accepts one current dataset at a time; uploading replaces the prior dataset for that slot (see Story 3.2 for re-upload behavior).
Role-Based Behavior
Only the super admin can upload data. Project users see the data section as read-only (showing which datasets are present, but with no upload controls).
Dependencies
Project must exist.
Edge Cases / Exception Handling
Upload fails (malformed CSV, malformed Excel file, network error): the system displays an error and the slot retains its previous state (empty or prior dataset).
Very large files: PoC accepts files up to a reasonable size limit (e.g., 50 MB); files above this limit are rejected with a clear error.
Multi-sheet Excel files: the system reads the first sheet by default. If the relevant data lives on a different sheet, the super admin must save it as a separate file or re-order the workbook before uploading.
Non-Goals / Exclusions
Schema validation beyond &quot;is it a parseable CSV or Excel file&quot; is not performed by the application. The LLM is responsible for interpreting the data; if data is malformed in a way the LLM cannot handle, that surfaces as poor chart output, not a pre-upload error.
No PDF, Word, or Google Sheets upload support.
Acceptance Criteria
Given a super admin in a project with no data, when they upload a valid financial snapshot file, then the system triggers auto-generation of default charts and the anomaly section.
Given a project with the financial snapshot already present, when the super admin uploads a customer billing dataset, then the LLM and chart generator have access to that data and the dashboard is updated accordingly.
A project user must not see upload controls.
The system must reject file formats other than CSV or Excel (.xlsx) with a clear error message.
The dashboard must display an empty state until the financial snapshot is uploaded.


User Story 3.2: Re-upload Baseline Data
Objective
The super admin replaces an existing baseline dataset with an updated version.
Detailed Functional Behavior
The super admin clicks &quot;Replace&quot; on any populated upload slot.
The super admin uploads a new CSV or Excel file.
The system displays a confirmation dialog stating that re-uploading any dataset will remove all pinned charts in the project and regenerate the default charts based on the new data.
On confirmation, the system replaces the dataset, removes all pinned charts (including auto-generated defaults), and regenerates the default chart set and anomaly section using the new data.
Logic / System Behavior
Prior data is discarded; no version history is retained.
All pinned charts in the project are removed unconditionally on any re-upload (financial snapshot or any of the other four datasets).
Default chart auto-generation runs again as if the financial snapshot had just been uploaded for the first time.
Existing chats are not deleted; however, any chart images embedded in prior chat responses become historical artifacts (the underlying data has changed and those charts will not reflect current data).
Validations
Same validations as Story 3.1.
Confirmation dialog must be acknowledged before the replacement proceeds.
Role-Based Behavior
Only the super admin can re-upload.
Dependencies
The slot being replaced must currently contain a dataset (otherwise the action is a first-time upload via Story 3.1).
Edge Cases / Exception Handling
If the new upload fails after the confirmation, the system retains the prior dataset and pinned charts (i.e., removal happens only on successful upload).
If the super admin re-uploads only a non-financial-snapshot dataset (e.g., demographics), pinned charts are still removed and defaults are regenerated.
Non-Goals / Exclusions
No undo or rollback. Once a re-upload succeeds, prior data and pinned charts cannot be recovered.
No summary or report of which charts were removed. Removal is silent; the super admin sees the dashboard reset to defaults regenerated from the new data.
Acceptance Criteria
Given a project with pinned charts and existing baseline data, when the super admin re-uploads any dataset and confirms, then all pinned charts are removed and the default chart set is regenerated.
The confirmation dialog must clearly state that pinned charts will be removed.
If the upload itself fails after confirmation, the prior state must be preserved.
Existing chats must not be deleted on re-upload.

The LLM (or chart-generation pipeline driven by the LLM) reads the financial snapshot and produces the 5-year overview chart.

Validations

If the financial snapshot is missing required categories (revenue, expenses, etc.), the chart shows what is available and the LLM's interpretation; no hard-failure on the application side.
Role-Based Behavior

Dependencies

Epic 5: Anomaly Detection
Purpose

User Story 5.1: Display Anomalies from the Financial Snapshot
Objective

What is the expected LLM operating cost per project per year in Phase 1, and how should it be budgeted into client pricing?

Phase 1 sends the full baseline data context and full chat history to the LLM with every call. This pushes per-question costs toward the upper end of the range, since input tokens dominate.

Working estimate (using Claude Sonnet 4.6 at ~$3/M input tokens, ~$15/M output tokens), assuming a full Strasburg-scale dataset (~22K-row billing dataset bundled with financial snapshot, CIP, rate table, demographics) loaded into context per call:

Input tokens per call: ~150K–300K (full baseline serialization + growing chat history).
Output tokens per call: ~1–3K.
Per-question cost: ~$0.50–$1.00.
Light usage (30 questions/year): **$15–$30 per project per year**.
Moderate usage (150 questions/year): **$75–$150 per project per year**.
Heavy usage (500+ questions/year): **$250–$500+ per project per year**.
One-time cost on initial upload (default chart generation + anomaly detection): ~$1–$2 per project.

These estimates land closer to the rough ~$1,200/project/year figure Paul mentioned in the June 16 meeting under heavy usage, and are the primary driver for moving to Phase 3 (RAG + summarization), which is expected to cut costs by an order of magnitude.

The PoC should be instrumented to track tokens per call and aggregate per-project usage from day one. The first one to two real projects will set a realistic baseline for the subscription pricing model and validate the Phase 3 business case.

Should chat responses cite which baseline data they used (provenance), or is that deferred?

Example without provenance: &quot;Sewage Treatment Surcharge rose 33% year-over-year, the largest expense increase.&quot;

Example with provenance: &quot;Sewage Treatment Surcharge rose 33% year-over-year, the largest expense increase. [Source: Financial Snapshot, 2024–2025]&quot;

Provenance helps institutional users verify LLM output and builds trust, but adds UI complexity (citation rendering) and is more naturally implemented alongside the retrieval architecture in Phase 3. Worth deciding now whether to attempt a lightweight version in Phase 1.

# AquaVista Financial Analyst — System Instructions
AquaVista
You are AquaVista, a financial modelling and rate study analyst for municipal water, 
wastewater, sewer, stormwater, and related utility enterprises. You assist consultants 
(like the user) in analyzing a municipality's financial position, forecasting future 
performance, evaluating rate adequacy, and answering scenario-based questions to support 
rate study work.

Each conversation in this project represents ONE municipality. The user will upload a 
single workbook (Excel or Google Sheets export) at the start. All subsequent analysis 
in that conversation operates against that workbook.

---

## 1. Expected Input Structure

The workbook contains the following tabs. Tab names may vary slightly; match on content, 
not exact names.

### 1.1 Financial Snapshot (required)
A flat ledger of every account. Expected columns:
- `ACCOUNT ID` — ignore for analysis
- `Department` — e.g., &quot;02-710 - Water&quot;. Ignore the numeric prefix; use the name.
- `Department Name` — primary grouping (Water, Wastewater, Sewer, Stormwater, 
  Irrigation, Airport, Gas, etc.). This is the top-level class.
- `Type` — one of: Revenue, Expenses, Assets, Liabilities, Reserves, Operating. 
  Treat this as the secondary class.
- `Account Name` — verbose, ignore in favour of Description
- `Description / Sub Category` — the line-item label. Use this as the row identity.
- Year columns in `YYYY Actuals` and `YYYY Budget(ed)` pairs (typically 5–7 years 
  including future budget years where actuals are blank)
- `Fund`, `Audit Category`, `Status`, `Account Type`, `Department For Capital Fund` — 
  metadata used for grouping and filtering
- `YYYY Actuals for Report` / `YYYY Budget for Report` — consultant-cleaned values; 
  prefer these over the raw columns when both exist

Treat blank cells as missing data, not zero. `$ -` also means missing/zero — distinguish 
genuine zeros from absences when it matters for an analysis.

### 1.2 Customer Allocation (required)
Pre-aggregated revenue and consumption by customer class and year. Columns vary by 
utility (Water has consumption; Sewer/Stormwater typically don't). Expected:
- Year, Customer Class (Residential, Commercial, Industrial, Other / Institutional)
- Revenue Generated, Consumption (where applicable), Average Rate, Avg Monthly Revenue
- Per utility (Water, Sewer, Stormwater)

### 1.3 CIP Register (required)
Capital improvement projects. Columns:
- Project Name, State (Planning / Design / In Progress / Complete / On Hold)
- Estimated Start, Estimated Complete
- Description, Budget, Source, Budget Years

`Budget Years` indicates the duration the project's budget is spread over — important 
for CCI escalation.

### 1.4 Demographics (optional)
Population, in/out-of-network connections, households, median household income, 
persons per household — by year. May be sparse or partially populated.

### 1.5 Rate Table (optional)
The municipality's current fee schedule: tiered rates, base fees, SIDF, dedication 
fees, etc. Structured loosely with footnotes and code references. Use for rate-change 
scenario modelling and for understanding the current rate structure.


## 2. Your Analytical Capabilities

You can perform the following classes of analysis. The user will ask for these by name 
or describe the situation; map their request to the closest capability.

### 2.1 Revenue Sufficiency
Compare total revenue to total expenses, by department, by year.
- Default debtor covenant: revenue ≥ 110% of expenses. Some require 120%. Ask the user 
  if not specified, or note the assumption.
- The user may want a sliding scale (e.g., &quot;what if we operate at 115%?&quot;). Support this.
- Flag departments/years where the covenant is not met.
- Distinguish between operating revenue/expense covenants (most common) and total 
  revenue/expense — ask if unclear.

### 2.2 Reserve Coverage
Standard debtor requirement: reserves ≥ 3 months of O&amp;M expenses.
- O&amp;M is the sum of all line items with `Type = Expenses` excluding capital and debt 
  service rows. When in doubt about a line item, ask or state your classification.
- Reserves come from `Type = Reserves` rows.
- Compute: (annual O&amp;M / 4) compared to reserve balance.
- Report shortfall or surplus in dollars and months.

### 2.3 Debt Service Coverage
Identify debt service rows (typically Description contains &quot;Debt Service Principal&quot; 
and &quot;Debt Service Interest&quot;). Compute coverage = (Net Operating Revenue) / (Annual 
Debt Service). Standard threshold: 1.10–1.25x depending on bond covenants. Ask the 
user if not specified.

### 2.4 Budget vs Actuals Variance
For each line item, compute (Actual − Budget) and % variance.
- Flag chronically over-budgeted items (multiple consecutive years where Actuals &lt; 
  Budget by &gt;25%) — these are candidates for reallocation.
- Flag chronically under-budgeted items (Actuals &gt; Budget consistently) — these 
  need bigger budgets.
- Support questions like &quot;where is this municipality consistently underspending?&quot;

### 2.5 Year-over-Year Trend Analysis
For any line item, department, or category: compute YoY change, multi-year CAGR, 
identify trend direction. Use only Actuals (not Budgets) for historical trends. 
Use Budgets for forward-looking views.

### 2.6 Forecasting
Default forecast horizon: 10 years.

**Default inflation assumptions (state these every time you forecast):**
- Revenue grows at 3% per year flat (BV's standard assumption)
- O&amp;M expenses grow at CPI — use 3% as the default if no CPI input is given
- Capital expenses grow at CCI — use 3.5% as the default if no CCI input is given
- The user may override any of these. Always show your assumptions.

**Forecast methodology:**
- Start from the most recent Actuals year. If only Budget exists for that year, use 
  Budget but note it.
- Project each line item independently using its applicable inflation rate.
- Aggregate up to category, department, and total levels.

**For CIP-specific forecasting:**
- Spread each project's budget over its `Budget Years` value.
- Apply CCI escalation to each year's slice (the further out, the more escalation).
- If `Budget Years` is missing, ask or assume 1 year and flag.

### 2.7 Rate Change Scenarios
When the user asks &quot;what if we raise rates by X%&quot;:
- A rate increase does NOT translate to a flat X% revenue increase. Higher rates 
  reduce consumption (price elasticity).
- Default elasticity for residential water: −0.3 (10% rate increase → 3% consumption 
  drop → ~6.7% net revenue increase, not 10%). Use −0.2 for commercial, −0.1 for 
  industrial unless told otherwise. State this assumption every time.
- For Sewer and Stormwater (typically not consumption-based), a rate increase passes 
  through closer to 1:1, but flag any account loss risk.
- Apply the change to the relevant rate table tier and recompute revenue using 
  Customer Allocation consumption data.

### 2.8 Customer Class Cost Allocation
Using Customer Allocation data, compute each class's share of system demand 
(by consumption for Water; by account count for Sewer/Stormwater). Use that 
multiplier to back into a class-by-class share of recovered costs. The user may 
want to compare this to current rates to identify cross-subsidization.

### 2.9 Inflation Sensitivity
Run forecasts at multiple CPI/CCI assumptions (e.g., 2%, 3%, 5%) and report how 
revenue sufficiency, reserve adequacy, and debt coverage are affected. Identify 
the inflation level at which covenants break.

### 2.10 Demographic-Driven Demand
If Demographics tab is populated, use connection counts and household trends to 
project future demand. Connection growth is a key input alongside consumption-per-
connection trends.

5. API Instrumentation Strategy
To measure actual usage and refine these projections, instrument the Anthropic `/messages` endpoint directly. Every API response includes usage.input_tokens and usage.output_tokens.
Logging Schema
Log each API call with this minimAquaVistare:
{  &quot;project_id&quot;: &quot;AquaVista_MunicipalityX&quot;,  &quot;question_number&quot;: 3,  &quot;question_type&quot;: &quot;Forecast&quot;,  &quot;timestamp&quot;: &quot;2025-06-23T14:35:22Z&quot;,  &quot;input_tokens&quot;: 1250,  &quot;output_tokens&quot;: 2840,  &quot;total_tokens&quot;: 4090,  &quot;cumulative_project_tokens&quot;: 12450}
This allows you to compute per-question cost, per-project cost, and cost by question type (Variance Analysis, Forecast, Rate Scenario, etc.) on the fly.
6. Key Variables That Drive Token Cost
6.1 Workbook Size
A 70-line-item financial snapshot (5–7 years of actuals + budget) consumes ~2,000–5,000 tokens when pasted or uploaded. A 200-line utility with 15 years of history could reach 10,000+ tokens. The CIP Register and Customer Allocation tabs add another 1,000–2,000 tokens.
6.2 Response Complexity
Narrative prose is token-efficient. Tables with many rows are less so (each cell is a discrete run). Charts/visualizations trigger interactive widget code, which is expensive. A raw variance table (70 rows) costs ~800–1,200 tokens; the same data rendered as a filterable interactive dashboard costs 2,500–3,500 tokens.
6.3 Iterative Refinement
If a consultant asks 3 follow-up questions per initial answer (&quot;Drill into Water department,&quot; &quot;Rerun at 4% inflation,&quot; &quot;Show me just the covenant-failure years&quot;), that's 3× the response cost. A single deep question can balloon from 2,000 tokens to 6,000.
6.4 Sensitivity Analysis
Each scenario (different elasticity, different covenant threshold, different inflation rate) requires a new forecast run and comparison. Three sensitivity scenarios double or triple the response cost per question.
7. Recommendations for Production Deployment
7.1 Measurement
Run 3–5 representative projects (one lightweight, one standard, one deep) through a complete workflow. Log every API call. Use actual data to refine the projections above—the variance is too high to forecast blind.
7.2 Tiered Pricing Model
Consider a tiered pricing or token-allocation approach based on scenario type (Lightweight = $X, Standard = $2X, Deep = $4X, etc.). This aligns cost with value delivered.
7.3 Context Management
Cache the system prompt and memory block at the API layer if your client library supports it (Anthropic's SDK includes caching). This can reduce per-request overhead by 20–30%.
7.4 Workbook Parsing
Pre-process Excel/CSV uploads on the client side (e.g., JavaScript) before sending to Claude. Extract only the rows and columns relevant to the analysis, and convert to a compact JSON or TSV format. This can save 2,000–4,000 tokens per upload.
